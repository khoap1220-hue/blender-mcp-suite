### 1.2 Communication Protocol & Architecture Analysis
Two distinct communication pipelines exist in the repository, each with fundamental incompatibilities:

#### Architecture A: `addon/blender_mcp.py` + `blender_mcp` package
1. **Transport**: Raw TCP socket on `127.0.0.1:9876`.
2. **Framing & Delimitation**:
   - `addon/blender_mcp.py` lines 698-718:
     ```python
     data = client.recv(8192)
     buffer += data
     try:
         command = json.loads(buffer.decode('utf-8'))
         buffer = b''
         self.command_queue.put((command, client))
     except (json.JSONDecodeError, UnicodeDecodeError):
         pass
     ```
   - Server does **not** use a packet delimiter; it attempts `json.loads` incrementally until valid JSON is parsed.
   - Response serialization (line 678): `client.sendall(response_json.encode('utf-8'))` (raw JSON, no newline, no null-byte).
3. **Threading Model & Main-Thread Execution**:
   - Background thread `_server_loop` accepts connections and spawns per-client worker threads `_handle_client`.
   - Worker thread queues commands into `self.command_queue = queue.Queue()`.
   - Execution is dispatched onto Blender's main thread via `bpy.app.timers.register(self._drain_command_queue, persistent=True)` running every 50ms.
4. **Fatal Headless Incompatibility**:
   - `addon/blender_mcp.py` lines 528-531:
     ```python
     if bpy.app.background:
         print("BlenderMCP: cannot start server in background mode (blender -b) - commands would never execute\n"
               "BlenderMCP: run Blender with a GUI, or use a virtual display: xvfb-run -a blender")
         return
     ```
   - In headless mode (`blender -b`), Blender does not run the window manager event loop that pumps `bpy.app.timers`. As a result, `addon/blender_mcp.py` **refuses to start**, completely blocking headless operation.
5. **Command Structure**:
   - Expects `{"type": "<command_name>", "params": {<kwargs>}}`.
   - Returns `{"status": "success", "result": ...}` or `{"status": "error", "message": ...}`.
   - For `execute_code`, returns `{"executed": True, "result": captured_output}` where `captured_output` is captured `sys.stdout` via `io.StringIO()`. **Values assigned to `result = ...` in code are discarded!**

#### Architecture B: `official_blender_lab_bridge.py`
1. **Transport**: Single-shot TCP connection per tool call to `127.0.0.1:9876`.
2. **Framing**:
   - Lines 42-50:
     ```python
     payload = json.dumps({"type": "execute", "code": code, "strict_json": strict_json}) + "\0"
     s.sendall(payload.encode("utf-8"))
     buf = bytearray()
     while b"\0" not in buf:
         chunk = s.recv(4096)
         buf.extend(chunk)
     ```
   - Requires null-byte `\0` delimiter on both requests and responses.
3. **Protocol Incompatibility with Addon A**:
   - `bridge.py` sends `{"type": "execute", ...}\0`, but `addon/blender_mcp.py` expects `{"type": "execute_code", "params": {...}}` without `\0`.
   - If `bridge.py` connects to `addon/blender_mcp.py`, the addon errors with `Unknown command type: execute` without returning a `\0`, causing `bridge.py` to hang until socket timeout (30 seconds)!

## 2. Logic Chain: Gap Analysis against Requirements (R1–R4)

### 2.1 Gap Analysis R1: Blender Daemon Lifecycle & Socket Auto-Recovery

```
Observation: C:\Program Files\Blender Foundation\Blender 4.1\blender.exe exists and runs.
Observation: addon/blender_mcp.py line 528: `if bpy.app.background: return` explicitly rejects headless mode.
Observation: Neither official_blender_lab_bridge.py nor blender_mcp_launcher.py has daemon auto-detection or subprocess management.
Observation: launch_blender.bat requires human manual interaction (launch GUI, press N, click Start MCP Server).
Observation: Socket connections fail with unhandled ConnectionRefusedError or socket.timeout; no retry loop exists.
```

**Logical Deduction**:
1. **No Headless Daemon Capability**: The system currently cannot operate autonomously in a headless CI or background environment. If the user does not open Blender GUI and manually click "Start MCP Server", all MCP operations fail immediately.
2. **Missing Lifecycle Manager**: There is no component that:
   - Checks if port 9876 is already servicing requests (e.g. user GUI session).
   - If not, auto-detects `blender.exe` (via standard installation paths, Windows Registry, or PATH) and launches a background daemon process.
   - In headless mode, Blender must run a dedicated Python script that maintains an active event/socket loop without needing `bpy.app.timers` or GUI window manager.
3. **No Auto-Recovery with Exponential Backoff**: When the socket drops or Blender is restarting, client requests crash. An auto-reconnection layer with exponential backoff (e.g. 100ms, 200ms, 400ms, 800ms, 1600ms up to 3s) is completely absent.
4. **No Graceful Shutdown & Zombie Prevention**: If the MCP server is killed, any spawned Blender processes could become orphaned zombies holding port 9876. A process lifecycle manager with `atexit`, signal handling, and clean port release is required.

### 2.3 Gap Analysis R3: Structured Error Handling & Zero-Crash Boundary

```
Observation: addon/blender_mcp.py line 675: `response_json = json.dumps({"status": "error", "message": str(e)})`
Observation: official_blender_lab_bridge.py line 71: returns string `ERROR: ...` inside TextContent without setting isError=True.
Observation: addon/blender_mcp.py execute_code discards return variables assigned in namespace.
Observation: Object lookups (bpy.data.objects.get) crash with unhandled NoneType errors if object doesn't exist.
```

**Logical Deduction**:
1. **MCP Protocol Violation**: The Model Context Protocol specification requires tools to return `CallToolResult(isError=True, content=[...])` when execution fails, enabling AI agents to recognize failures and self-correct. Returning errors as plain text with `isError=False` confuses client LLMs.
2. **Missing Standard Error Codes**: No error taxonomy exists. The system needs standardized error codes:
   - `ERR_OBJECT_NOT_FOUND`
   - `ERR_INVALID_PARAMETERS`
   - `ERR_CONTEXT_INVALID`
   - `ERR_EXECUTION_FAILED`
   - `ERR_BLENDER_DISCONNECTED`
   - `ERR_RENDER_FAILED`
3. **Zero-Crash Boundary in Blender**:
   - Any `bpy` execution must operate within an isolated safe context wrapper.
   - Active object and context override guards must ensure operators do not fail when `context.active_object` or `context.selected_objects` is empty.
   - Unhandled exceptions must be trapped at the boundary, formatted into structured JSON-RPC responses, and must never terminate the socket listener thread or background daemon.

## 3. Caveats

1. **Blender 4.1 UI vs Headless Event Loops**: In Blender GUI mode, `bpy.app.timers` runs inside the main window manager loop. In headless mode (`blender -b`), Blender exits as soon as the script finishes unless a dedicated polling/event loop keeps the main thread alive. The daemon server must provide an event pump or queue drain loop for headless mode.
2. **GPU / OpenGL Offscreen Capture**: In headless mode on Windows without a display attached, `gpu.types.GPUOffScreen` and `bpy.ops.screen.screenshot_area` may fail if no OpenGL hardware context is available. The viewport capture tool must gracefully fall back to `bpy.ops.render.render(write_still=True)` using EEVEE or Cycles CPU/GPU.
3. **Port Collisions**: Port 9876 may occasionally remain in `TIME_WAIT` after a socket closes. Socket creation must use `SO_REUSEADDR` and connection retries must account for TCP socket teardown latencies.
